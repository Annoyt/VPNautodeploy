## A. Качество защиты от DPI

### A1 (P0). Замкнуть фидбэк-петлю: авто-ротация каскада по ASN

**Проблема (актуальна на 2026-08-30).** Телеметрии стало ВТРОЕ больше — отчёты
юзеров (`user_failure_reports` с country/asn/city), 5-минутные срезы
`dpi_metrics` (conn / short-session / handshake-fail / rst по (country, ASN)) и
пробы через реальные туннели — но на выдачу по-прежнему не влияет ничего:
`cascade_by_asn` правит только оператор руками (`get_asn_cascade` в
`handlers/callbacks/user.py:725` — read-only потребитель), юзер вручную жмёт
«try_alt». **Это главный незакрытый разрыв проекта.**

**Что сделать.** Фоновая задача `DPIMonitor` (тред из `init_services` либо
APScheduler-джоба рядом с `_dpi_collect_sync` в `notifications.py` — там уже
крутится сбор):
1. Раз в N минут агрегирует за скользящее окно (2 ч) **два источника**:
   `dpi_metrics` по `(country, asn)` — доля коротких сессий и handshake-fail'ов,
   и `user_failure_reports` по `(asn, protocol_hint)`.
2. Если когорта пробивает порог (та же логика, что у алертов: ≥0.40 short-ratio
   при `conn_count ≥ 50`, либо ≥5× handshake-fail к базовой линии) — переставляет
   проблемный протокол вниз `cascade_by_asn` для этого ASN и поднимает тот, что
   зонд сейчас считает живым.
3. Пишет изменение в `app_settings.cascade_by_asn` (механизм готов) + строку в
   `admin_actions`, и уведомляет админа в топик — авто-действие должно быть видимым.
4. Гистерезис: не дёргать порядок чаще раза в X минут на ASN; требовать
   подтверждения трендом (2 цикла подряд, как уже сделано для алертов), иначе
   один всплеск расколбасит выдачу.
5. Тестировать по 2-му уровню (реальный SQLite): засеять `dpi_metrics`, прогнать
   монитор, проверить итоговый JSON каскада.

**Почему это P0.** Это единственное изменение, которое превращает уже собранные
данные в самонастраивающуюся систему. РКН тюнит блокировки по операторам (ASN) —
здесь мы отвечаем в той же гранулярности и автоматически.

**Точки входа:** `bot/handlers/callbacks/user.py::get_asn_cascade / get_cascade_order`
(читатель уже готов), новый `bot/services/dpi_monitor.py`, `main.py::init_services`.

### A2 (✅ СДЕЛАНО 2026-08). Активный зонд протоколов с entry-узла

Реализовано как **probe-proxy сайдкар** на entry: sing-box с конфигом,
генерируемым `scripts/gen_probe_config.py` (по одному outbound на протокол
каскада), HealthChecker ходит через реальные туннели per-protocol, а не
TCP-коннектом «порт открыт» (та самая ловушка «Connected без туннеля»).
`scripts/exit_dpi_reporter.py` + таблица `dpi_metrics` дают срез с exit-стороны.

**Остаток (P2):** entry видит только свой ASN. Несколько vantage-точек у разных
РФ-операторов дали бы настоящую карту блокировок — дешёвые VPS только под зонды,
без трафика. Пока не критично: `dpi_metrics` по (country, ASN) частично
компенсирует за счёт реальных когорт пользователей.

### A3 (✅ СДЕЛАНО 2026-07/08). Hysteria2: обфускация + port hopping

Сделано всё три пункта и сверх того:
- `obfs=salamander` (`HY2_OBFS_PASSWORD`) — сырые hy2-ссылки без него были
  мертвы после включения salamander на сервере;
- port hopping через `HY2_HOP_PORTS`. **Грабля**: формат разный у sing-box
  (`server_ports` — массив `"X:Y"`) и у URI (`mport` — строка через запятую);
  их смешение уронило Hy2 26.07 (см. память `project_hy2_hop_ports_format`);
- Brutal CC приехал в виде **отдельного инстанса hy2t «Turbo»** на exit :8402 —
  paid-дефолт, обычный hy2 отдан freemium. Auth разведён по эндпоинтам
  (`/api/hy2/auth` demo+paid vs `/api/hy2t/auth` только paid).

### A4 (⚠️ ЧАСТИЧНО). Reality: гигиена SNI/short_id

**Сделано (вынужденно, 2026-07-20).** Ушли с `www.microsoft.com` на
`www.bing.com` — но не из-за заезженности, а из-за инцидента: Microsoft
обновила цепочку сертификатов, TLS-запись выросла до 8273 байт и перестала
влезать в хардкод `size = 8192` в xtls/reality → Reality лёг у ВСЕХ.
**Урок в план:** перед сменой dest проверять размер записи
(`openssl s_client … | grep -A1 'Certificate$'`, надо ≤ ~8000 B), и менять SNI
синхронно в трёх местах (панель exit, HAProxy ACL на entry, `SNI_VALUE` в .env).

**Осталось (P1).**
- Пул `short_id` (Reality поддерживает несколько) — разный per-user.
- Рандомизация `fp` (chrome/firefox/safari/ios) между пользователями.
- Мониторить размер сертификата текущего dest автоматически (проба раз в сутки,
  алерт при приближении к лимиту) — чтобы §23 не повторился «внезапно».

### A5 (P1). Новые/усиленные транспорты в каскаде

- **AmneziaWG** (P1) — WireGuard с DPI-обфускацией (junk-пакеты, magic headers,
  кастомные размеры). Уже в списке ресурсов проекта, но не внедрён. Хорош как
  «последний рубеж» и как whole-device вариант. Добавить как протокол каскада
  `awg` со своим builder-ом и env-гейтом (по образцу `hy2`/`stls`).
- **TUIC v5** (P2) — альтернативный UDP-протокол на случай, если Hy2-сигнатуру
  начнут ловить. Разнообразие UDP-профилей.
- **VLESS+XHTTP напрямую (не только через CF)** (P2) — новейший транспорт, режим
  `packet-up/stream-up`, устойчив и с CDN, и без. Сейчас xhttp только через CF.

### A6 (P2). Padding и фрагментация

- `tls.fragment` сейчас голый boolean (`_TLS_FRAGMENT`) и работает **только у тех,
  кто через подписку sing-box**. Пользователи с «сырой» VLESS-ссылкой фрагментации
  не получают. Вывод: в UX подталкивать всех на подписку (см. C-раздел), а не на
  ручную ссылку.
- Добавить padding: XTLS Vision padding для Reality, `obfs`/padding у Hy2 (см. A3),
  чтобы сбить статистический анализ размеров пакетов.

## B. Обход белых списков (whitelist / lockdown-режим)

«Белые списки» = сценарий, когда сеть пропускает **только** разрешённые
назначения (RU-домены, госуслуги, банки, отдельные CDN), всё остальное — reject
по умолчанию. Это худший случай (региональные шатдауны, «суверенный интернет»).
Против него работает не «спрятать протокол», а **пролезть через разрешённое**.

### B1 (P0). Явный режим «lockdown» + авто-детект шатдауна

**Что сделать.**
- Добавить в `app_settings` флаг `lockdown_mode` и специальный каскад
  `LOCKDOWN_CASCADE`, который ставит наверх **только** протоколы, пролезающие
  через whitelist: CF-фронтинг (`ws`/`xhttp`) и ShadowTLS с whitelisted-SNI;
  прямые-к-entry (`reality`/`hy2`) уходят вниз или отключаются. Механизм каскадов
  уже есть — это ещё один слой поверх `get_cascade_order`.
- **Авто-детект:** DPIMonitor (A1) видит одновременный всплеск отказов по многим
  ASN за короткое окно → это не точечный бан, а массовый шатдаун → авто-включает
  `lockdown_mode`, шлёт админу алерт и (опц.) уведомляет юзеров «включили
  устойчивый режим, обнови подписку».

### B2 (P0/P1). Фронтинг через реально разрешённое

- **Cloudflare как несущая.** У вас уже есть CF-фронтинг (`cdn.nekoweather.xyz`).
  В whitelist-режиме ключевой вопрос — попадёт ли CF под белый список. Многие
  РФ-сервисы висят за CF, поэтому его тотальный блок = большой сопутствующий
  ущерб. В lockdown делаем CF-путь **основным** и держим домен-фронт с высоким
  collateral.
- **Whitelisted-SNI для ShadowTLS/Reality.** Сейчас `STLS_SNI=www.microsoft.com`.
  В lockdown толку от microsoft мало (может не быть в белом списке). Нужна
  возможность задать SNI домена, который **точно** в белом списке РФ (крупный
  отечественный/инфраструктурный ресурс). Сделать `STLS_SNI`/`SNI_VALUE`
  переключаемыми под lockdown-профиль.

### B3 (P1). Диверсификация CDN

Один фронт (Cloudflare) — единая точка отказа. Добавить второй CDN-фронт (другой
провайдер) как параллельный outbound в подписке. Если CF задушат/замедлят —
второй несёт. Плюс вариант **Cloudflare Worker как релей** (домен-фронтинг на
воркере), чтобы даже при блоке origin-порта трафик шёл через воркерский путь.

### B4 (P2). DNS-туннель как абсолютный последний рубеж

Когда пропускают только DNS/разрешённый резолвер — медленный, но работающий
DNS-туннель (или DoH через whitelisted-резолвер) даёт хотя бы мессенджеры.
Отдельный аварийный outbound, включаемый вручную/в lockdown. Низкий приоритет:
дорого по UX, но это буквально «последняя миля» при полном whitelist.

### B5. Роутинг под lockdown

В lockdown-профиле подписки: `final=proxy` для всего (кроме явного RU-direct
allow-list, чтобы разрешённое не ломать), remote-DNS через прокси. Сейчас
routing заточен под «обычный» режим (RU-direct, `final=local`) — под lockdown
нужен второй набор правил в `_build_route_rules`, выбираемый по флагу.

## C. Бот и инфраструктура

### C1 (P1). Оживить multi-node failover + ротация entry-IP

**Проблема.** Весь cluster-код (`bot/core/cluster/*`, `_generate_multi_node_link`)
**мёртв** — не инстанцируется в проде (см. AGENTS.md §5). Хендлеры зовут legacy
`generate_vless_link`. Один exit-узел = единая точка отказа, а Reality банится
по entry-IP первым.

**Что сделать.** Поднять реальный второй exit + ≥2 entry-IP, подключить
`NodeManager`/`SmartRouting` в `init_services`, реализовать `QuotaMonitor`
(миграция по 95% квоты из 3x-ui, батчами по 10, UUID сохраняется — по
согласованным ранее правилам). Когда entry-IP профилируется — авто-своп на
запасной без переиздачи ключа (подписка сама подтянет новый IP).

### C2 (P1). Наблюдаемость: дашборд успешности по протоколу/ASN

`bot/utils/prometheus.py` уже есть. Экспортировать метрики: success-rate по
протоколу × ASN (из `user_failure_reports` + зонда A2), статус lockdown, живость
entry-IP. Оператор видит деградацию **до** волны жалоб. Это глаза для A1/A2/B1.

**Что уже закрыто (2026-09-05).** Живость *по протоколу* с точки зрения entry:
`outbound_health` → алерт `protocol_down:*` (critical, в топик AI, с
авто-диагностикой агентом) → `/protocols` в боте → `protocol_healthcheck.py`
как первый шаг любой диагностики; целостность per-client полей панели —
`verify_panel_client_fields.py` (post-deploy smoke). «Протокол лёг» теперь
виден за ~час, а не через 4 дня, и не зависит от того, посмотрел ли кто-то на
дашборд.

**Что остаётся открытым.** Сам дашборд/экспорт **success-rate по протоколу ×
ASN** — не сделан: пробы видят только ASN entry, а деградацию у конкретного
оператора по-прежнему видно лишь по жалобам (`user_failure_reports`) постфактум.
Также нет статуса lockdown и живости entry-IP как метрик. Это и есть остаток C2.

### C3 (P0, повышен). CI + тест-бот

**Что изменилось.** Тестовая пирамида построена (4 уровня, ~2050 + 6 E2E,
см. PROJECT.md §8), деплой сверяет sha. Но **прогоняет всё это человек руками** —
CI-раннера нет вообще (`.github/workflows/` отсутствует). Один забытый прогон
перед `deploy_to_entry.sh` — и уровни 1–3 бесполезны.

**Что сделать (S–M).**
1. GitHub Actions на push/PR: `pytest tests/ -q` + отдельным job'ом
   `pytest tests/e2e -q` (с `playwright install chromium`, кэш браузера).
   Ветка не мержится красной.
2. Мутационный гейт по-дешёвому: mutmut только на изменённых файлах в PR.
3. Тест-бот `@test_nekovpn_bot` + тестовый инбаунд на exit — чтобы протокольные
   правки (SNI, hop-порты, форматы `/sub`) проверялись на живом клиенте до прода.
   Именно этот класс багов тесты не ловят в принципе.

### C4 (P2). UX: тянуть всех на подписку, а не на «сырую» ссылку

Фрагментация/ECH/весь каскад доступны **только через подписку** sing-box. Кто
скопировал одиночную VLESS-ссылку — теряет защиту. `/mykey` и онбординг должны
по умолчанию выдавать subscription-URL (одна ссылка = весь каскад +
авто-обновление при ротации IP), а одиночные ссылки — только как запасной вариант.

### C5 (P2). Технический долг и безопасность

- **Token-lookup O(n)** — всё ещё открыт. `SubscriptionService.find_user_by_token`
  (`subscription.py:58`) на КАЖДЫЙ refresh `/sub` тянет всех юзеров и хэширует их
  uuid'ы. При 150 юзерах терпимо, при 1000+ — заметно. Индексированная колонка
  `sub_token` (заполняется при выдаче ключа) или кэш; сравнение оставить
  constant-time.
- **Дрейф прод-конфигов** (новое). `docker-compose.yml` на entry расходится с
  репо (ручные HTTPS_PROXY/WEB_BIND), панель exit имеет инбаунды 4/5/6, про
  которые `sync_all_clients_from_bot_db` не знает (сверяет только inbound 1) —
  «один протокол работает, другой нет» диагностируется только ручным диффом
  членства. Нужен аудит-скрипт «кто в каком инбаунде» + отчёт расхождений.
  (2026-09-05: *поля* клиентов теперь аудирует `verify_panel_client_fields.py`;
  *членство* по инбаундам — всё ещё нет.)
- **Ёмкость почты** (новое). Gmail-релей ~500 писем/день на всё: ключи,
  квота-алерты, продления. При росте ext_*-базы упрёмся; план Б — платный
  transactional-провайдер (свой MTA невозможен, у entry нет PTR).
- ✅ **Платежи** — закрыто (Stars + `grant_paid_access` + месячные джобы).
- ✅ **Безопасность AI-агента** — в основном закрыто (Hermes smart-approvals,
  hardline-блоклист, запреты в skills). Остаток: агент по-прежнему root на entry
  без изоляции — при желании ужесточать через `terminal.backend: docker`.

## D. Разгрузка exit-нод, миграция и оркестрация развёртывания

Это отдельное направление: как раскидать нагрузку и как разворачивать так, чтобы
тяжёлые части оказывались именно там, где нужно.

### D0. Модель: control-plane vs data-plane (концептуальная основа)

Сейчас **бот + БД + 3x-ui + xray живут на одном exit-узле** — управляющая логика
приклеена к одной data-plane-машине. Это и есть корень проблемы разгрузки: нельзя
масштабировать egress, не таща за собой бота и БД, и нельзя обновлять бота, не
трогая работающий туннель.

Целевое разделение на три роли (каждая — со своим «весом» нагрузки):

| Роль | Что несёт | Нагрузка | Свойства |
|------|-----------|----------|----------|
| **control** | бот, SQLite/БД, дашборд, DPIMonitor, AI-агент, генератор подписок | RAM/IO, не latency-critical для туннеля | одна штука, стабильная, может быть вне РФ |
| **exit** | 3x-ui + xray (реальный egress, крипто) | **CPU-bound**, растёт с числом юзеров | N штук, балансируются, мигрируются |
| **entry** | RU-фронтенды: DNAT / Reality-frontend / ShadowTLS / HAProxy + зонд A2 | лёгкая (форвардинг) | дешёвые, одноразовые, ротируются при бане IP |

Принцип: **высоконагруженное крипто — на exit (или выделенный exit-пул), stateful
control — на отдельной ноде, entry держим тонким и одноразовым.** Тогда бан entry-IP
= замена дешёвой ноды без переустановки бота, а рост юзеров = добавление exit без
касания control-plane.

### D1 (P1). Взвешенный least-loaded выбор exit + реальная нагрузка

**Проблема.** `VPNNode` уже имеет `weight / max_clients / current_clients /
is_available`, а `performance_monitor.select_best_exit_node` умеет выбирать
наименее загруженный — но это мёртвый код, `current_clients` в проде никто не
заполняет, выдача идёт через legacy `generate_vless_link` на единственный exit.

**Что сделать.**
1. Заполнять реальную нагрузку exit-узла: не только счётчик клиентов, а
   композитный скор из **CPU (`bot/utils/metrics/proc_reader.py`), суммарного
   трафика из 3x-ui, throttle-статуса** (`node_tracker.py` это уже умеет).
2. При назначении нового юзера — взвешенный least-loaded выбор среди
   `is_available` exit-узлов (учитывая `weight`, чтобы более мощные VPS брали
   больше). Функция уже есть — подключить в `find_best_exit_for_user`.
3. Порог перегрузки (`max_clients` / CPU-cap) → узел выпадает из выдачи новых, но
   продолжает обслуживать текущих. При спаде — возвращается.

### D2 (P1). QuotaMonitor + миграция (квота / нагрузка / drain)

**Что сделать.** Фоновый `QuotaMonitor` (тред из `init_services`, как остальные
async-задачи), три триггера миграции:
- **По квоте** — узел >95% месячного лимита из 3x-ui (уже согласованное правило).
- **По нагрузке** — узел устойчиво перегружен (из D1) → часть юзеров на менее
  загруженный.
- **Drain / обслуживание** — `status=maintenance` → мягкая эвакуация всех юзеров
  перед выводом узла (обновление, замена, бан IP).

Все миграции по согласованным правилам: **батчами по 10, последовательно, с паузой
5–10 c, UUID и email сохраняются** (юзеру ничего переустанавливать не надо —
подписка сама подтянет новые pbk/sni/sid/port). Событие пишется в
`node_failover_log`. Для юзеров на подписке миграция вообще незаметна.

### D3 (P1). Role-aware установщик и деплой

**Проблема.** `install.sh` монолитный — ставит docker+3x-ui+бот+caddy+агент на один
хост. `deploy_both_nodes.sh` льёт **один и тот же код** на обе ноды, entry
конфигурится вручную. Понятия «footprint роли» нет.

**Что сделать.**
1. `install.sh --role control|exit|entry` (по умолчанию `all-in-one` = текущее
   поведение, чтобы не сломать одно-хостовые установки). Каждая роль ставит только
   свой набор:
   - `control` → бот, БД-volume, Caddy/дашборд, DPIMonitor, (опц.) AI-агент.
   - `exit` → 3x-ui + xray + traffic-collector; регистрируется в `nodes` через
     control-plane API.
   - `entry` → xray-frontend (Reality/ShadowTLS/HAProxy) + iptables + зонд A2;
     ставится в минимальном footprint, без 3x-ui и бота.
2. Профили docker-compose (`--profile control|exit|entry`) вместо одного общего
   стека — каждый узел поднимает только свои сервисы.
3. Реестр нод как источник правды: control-plane знает host/role/capacity/status
   каждой ноды (таблица `nodes` уже есть) и раздаёт конфиги.

### D4 (P1). «Куда отправлять агента» — оркестратор размещения

Обобщить уже существующий `KIMI_NODE_TYPE=entry|exit` (+ SSHFS) до общего механизма
размещения агентов/задач по ролям:
- **AI-агент** → на `control` (доступ к БД/репо/деплою) ИЛИ на `entry` (если нужен
  прямой доступ к xray-логам изнутри РФ — текущий кейс). Выбор — явный флаг, а не
  хардкод; SSHFS остаётся мостом, когда агент и данные на разных узлах.
- **Зонд A2** → всегда на `entry` (нужна RU-точка обзора).
- **DPIMonitor / QuotaMonitor** → на `control` (нужны БД и агрегаты).
- **traffic-collector** → на каждом `exit` (локальный доступ к x-ui.db).

Итог: у оператора — таблица «компонент → целевая роль», а `install.sh`/оркестратор
раскладывает высоконагруженные части ровно туда, где им место. Добавление нового
exit или замена сгоревшего entry становится одной командой с указанием роли и хоста.

### D5 (P2). Гео-/латентность-осведомлённый выбор и авто-провижн

- Выбор exit не только по нагрузке, но и по близости к юзеру (`region/city` в
  `VPNNode` + `last_country/last_city` юзера уже есть) — меньше RTT.
- Авто-провижн exit через API провайдера (проверено: у AdminVPS API есть,
  у BitCloud — нет; DO/Hetzner/Linode из РФ не проверялись):
  при устойчивой перегрузке пула control-plane сам поднимает новый exit, гоняет
  `install.sh --role exit`, регистрирует и вводит в ротацию. Верхний уровень
  автоматизации — делать в последнюю очередь, когда ручной путь D3 отлажен.

## Принципы (чтобы улучшения не деградировали)

1. **Разнообразие важнее «идеального» протокола.** Цензор ломает по одному;
   параллельные непохожие профили (TCP-Reality, UDP-Hy2, CDN-VMess, SS-ShadowTLS,
   WG-Amnezia) переживают потерю любого одного.
2. **Гранулярность = ASN.** РКН тюнит по операторам — вся адаптация должна быть
   на уровне ASN, а не только страны (инфраструктура для этого уже есть).
3. **Фидбэк должен замыкаться автоматически.** Данные без авто-реакции = мёртвый
   груз; сейчас это главный незакрытый разрыв.
4. **Через whitelist проходят только через разрешённое** (CDN с высоким
   collateral, whitelisted-SNI), а не через «более скрытный» протокол.
5. **Каждое изменение протокола — с тестом и на тест-боте.** История прод-поломок
   в AGENTS.md показывает: молчаливые фейлы (sid=01, TLS-masquerade «Connected»
   без туннеля) стоят часов.
6. **Каждый слой тестируется своим уровнем.** Юниты на моках не видят
   межслойных эффектов, а питон-тесты вообще не видят фронтенд: 2026-08-30 три
   бага дашборда прожили месяцы при 1789 зелёных тестах. Новому сьюту доверять
   только после «верни баг — убедись, что покраснел» (PROJECT.md §8).
7. **Сделано = задеплоено и проверено на проде.** Фикс, лежащий в репо, не
   существует: `/opt/vpn-bot` — rsync-копия, и один фикс так пролежал 11 дней.
   `deploy_to_entry.sh` сверяет sha в `/health` — обходить его не надо.
