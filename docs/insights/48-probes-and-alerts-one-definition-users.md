# §48. Probes and alerts: one definition, users' connections, state that survives a restart (2026-11-11, plan F, package B)

The probes saw only what the entry datacenter sees, and the readers of the probe rows disagreed with each other. The alert manager also lost its state on every restart. Package B of `docs/IMPROVEMENT_PLAN.md` section F.

- **One definition of what the probe rows say** (B5): `bot/services/probe_rules.py`. It is stdlib-only, because `scripts/protocol_healthcheck.py` runs on the entry host and loads it by path.
  - `judge_window(rows)`: the newest 3 runs, newest first. `thin` = fewer than 15 rows (no verdict), `dark` = no live row (liveness: `latency_ms IS NOT NULL OR status='ok'`), `degraded` = at least 25 rows and fewer than 25 % ok, else `ok`.
  - `last_run_dark(rows)`: the newest full run had no ok. This is an early sign, not a verdict; `/protocols` shows it as "последний прогон без единого ответа".
  - The pager, DPIMonitor, `/protocols` + `/sos` and the agent's script all use it. Until now each kept its own copy: the script called below 35 % degraded, and `/protocols` called below half of the last run degraded.
- **The prober** (B1, `health_checker.py`):
  - The ten targets are `probe_rules.PROBE_TARGETS`. vk.com (418 to every probe) and sberbank.ru (a chain from the Russian national CA) never passed through the exit, so 8/10 was the norm; they are replaced by discord.com and x.com, and the norm is 10/10.
  - Every request of a run starts at once (one connection per target), so `TIMEOUT_SEC` is each request's own. Before, five connections served ten requests and the wait counted inside the 10 s: a path answering in 6 s read as 2/10, i.e. degraded.
  - **Bulk probe:** after the HEADs, one download of 128 KB per protocol (`BULK_URL`, Cloudflare's speed endpoint) into the new table `outbound_bulk` (`ok` / `partial` / `timeout` / `error` / `proxy_down`), never into `outbound_health`, whose ten rows a run the thresholds count. A HEAD cannot show the freeze after ~16 KB reported on Russian networks; `partial` is that signature. `/protocols` prints it when it is not `ok`. No pager alert; since 2026-11-13 DPIMonitor acts on it (`probe_bulk`, §55).
- **The DE reserve is probed** (B6): tag `de` (`probe_rules.RESERVE_TAG`), sidecar port 18086, wherever `FALLBACK_NODE_HOST` + `FALLBACK_NODE_PBK` are set.
  - `gen_probe_config.py` builds the paid users' DE outbound for the probe user and provisions it on the reserve's panel first (`ensure_client`).
  - The pager pages it as «Резерв DE не отвечает». It never counts in "every protocol dark at once" (exit down leaves it alive by design), and DPIMonitor never demotes it.
  - **Deploy order:** regenerate the probe config (gen_probe_config.py → probe-proxy restart, AGENTS.md §28) after the bot. Until then the checker gets `proxy_down` for every DE probe and writes nothing for it, so there is no false page.
- **Operator-disabled protocols** (B4, problem 7): `probe_rules.operator_disabled(cascade_protocol_order)`. The pager does not page them, and DPIMonitor neither measures nor demotes them. It answers exactly what the cascade editor (`get_cascade_config`) shows: a name counts by its first entry, a bare name is on, and an opt-in protocol (`probe_rules.OPT_IN_PROTOCOLS`, the editor's own tuple; today xhr) is off until an entry switches it on, a missing or unreadable setting included. Until 2026-11-12 a saved list that predated xhr made it count as on: its server lists nobody while xhr is off, so its dark probe would have paged critical and been demoted (prod's list had no xhr entry; the probe sidecar was stopped until this fix). `test_off_is_what_the_cascade_editor_shows` pins the two to each other. hy2t has been off since 2026-09-21 while its instance and probe stay up; a dark hy2t probe would have paged critical every 2 h. A switched-off protocol that still answers does count as evidence: it proves the channel up, so the pager does not call the rest «все протоколы молчат». The agent's script likewise leaves the DE reserve out of its all-dark rule, as the pager does.
  - **The other readers, since 2026-11-13.** `/protocols` shows a switched-off protocol as «⏸ выключен в каскаде, алертов нет» with its newest run, never red. The agent's script gives it state OFF: its facts stay as evidence, but it is outside the exit code, the ИТОГ line («…; выключены в каскаде: hy2t, xhr») and its all-dark rule, which, like the pager's, needs two protocols that are on and counts a switched-off one that answers as proof the channel is up. Without layer A the script cannot read the cascade, and nothing is OFF. Until then both called xhr dead while it was off (the card «лежит», the ИТОГ «xhr DOWN», exit 1), so the probe sidecar stayed stopped. `test_every_reader_leaves_a_switched_off_protocol_alone` feeds the same rows to all four readers.
- **Every probe alert carries every protocol's numbers** (B3): "Сейчас по пробам: hy2 ok 0/30 (живых 0) · hy2t выключен · reality ok 24/30 · …".
- **Users' connections on an exit inbound** (B2): `check_inbound_drop`, keys `inbound_drop:<proto>`, critical.
  - Rule: four 2-h blocks in a row (8 h), each below a fifth of the median of the same clock block on 7 earlier days, median ≥ 50, from `dpi_metrics` (exit-accepted connections; hy2 = the bot's rollup of hy2 auth allows).
  - **The baseline** is the 7 most recent USABLE days of that block, looked for up to 21 days back; fewer than 4 usable = no verdict. Not usable: a block the exit did not report, and a block of the key's current or last incident (`alert_state.opened_ts` .. `closed_ts`, plus the 8 h that opened it). Until this, an outage's own zeros entered the median: an 84-h ws outage would have "recovered" on day four, and a second drop within a week after a recovery went unseen.
  - Backtest on 30 days of prod (read-only, 2026-11-10): four blocks catch only the 29.10–02.11 ws outage, at 22:00 on 29.10. Three blocks also fired for an hour each on reality 29.10, ss2022 08.11 and cf-ws 09.11.
  - **"The exit did not report" is not "nobody connected":** new table `exit_reports`, one row per report, written by `/api/dpi/exit_report` even when the report is empty. A block counts only with ≥ 12 of its 24 reports; before the table existed, exit-tagged snapshots stand in. A block without reports gives no verdict, and an open alert stays as it was, across a restart too. A reporter silent for 30 min pages `inbound_drop:no_reports` (warn), but only once a report has ever come. Eight hours of reports without a single row page `inbound_drop:empty_reports` (warn) instead of every exit inbound at once: the reporter reads nothing. Neither of the two starts an agent turn. hy2 blocks count only while the bot itself was up; its alert says «Авторизации hy2 упали» (the bot's own journal, not exit).
  - Recomputed every 10 min. It kicks the protocol agent; it is an alert only, never a DPIMonitor rule (a demotion moves users off, the count falls, the rule would hold itself).
  - **A protocol demoted for everyone gives no verdict (2026-11-15).** ws, demoted by hand on 11-13 (§55), paged «Подключения ws на exit упали» critical every 2 h for days: its users had left it because of the demotion.
    - While a protocol is demoted for everyone (the global part of `cascade_manual` or `cascade_auto`), its key gets no verdict. A demotion for one network does not count: an inbound counts every network's users.
    - The same holds for a tail after the demotion ends. The tail is as long as the demotion was, at most `INBOUND_DROP_DEMOTION_TAIL_H` (24 h): a client takes the protocol back only at its next profile fetch, and FlClash fetches once a day. So the first verdict after a long demotion comes 32 h after it ends (the tail plus the 8-h window).
    - An alert already open stays open, with no repeats and no «✅ Восстановилось», until it is judged again after the tail.
    - Demoted blocks and their tail stay out of the baseline too. Otherwise a week-long demotion would set "usual" to the demoted level, below the 50 that proves anything.
    - The stores keep only the demotions in force, so each recompute samples them into `app_settings.cascade_demotion_spans` (`bot/services/demotion_spans.py`): `{proto: [[start, end | null], …]}`, naive UTC, kept 23 days, a new span starting at the store's `since`. A failed write costs only that sample.
    - Lockdown is not a demotion: a drop of the direct protocols under it is still paged.
    - Tests: `TestInboundDropWhileDemoted` in `tests/integration/test_alert_no_verdict.py` (real sqlite) and `tests/unit/test_demotion_spans.py`; 28 mutants killed (the window, the baseline, the tail and its cap, both stores, one network, the journal's sampling, pruning and failures), restored by a positional reverse replacement with a hash check.
  - `scripts/exit_dpi_reporter.py` now posts every run, an empty window too; before, a quiet window sent nothing and would read as a missing report. **It runs on exit** (`/usr/local/bin`, timer `exit-dpi-reporter`): copy it there when deploying this; until then a quiet exit only makes blocks "no verdict", never a false page.
- **AlertManager** (B3, B4):
  - New table `alert_state`: `last_fired_ts`, `acked_until_ts`, `open`, `notify`, `title`, `opened_ts`, `closed_ts` per key, loaded at start and saved on fire, ack and recovery. A restart during an outage no longer re-pages the key or starts another agent turn, and an ack holds. Streak counters stay in memory.
  - **"Could not look" is never "recovered".** A multi-bucket check may return `(prefix, alerts, judged)`: only the keys in `judged` heal when absent; every other key under the prefix keeps its state (no healthy tick, no recovery, no fire). The probe check judges nothing on a failed read or stale probes, only `probe_pipeline` while every protocol is dark, and no key of a protocol whose window is thin. The inbound-drop check judges no key whose blocks lack reports or history. Before this, «✅ Восстановилось» was posted after each of those, and the cleared cooldown re-paged the key when the real state came back.
  - **Recovery:** an open `protocol_down:*` / `inbound_drop:*` alert judged quiet for `RECOVERY_TICKS` (5) ticks posts «✅ Восстановилось: <title>» where it went, if it went to the chat. Its repeat cooldown and its ack are cleared, so a new failure pages at once. Other families keep both on close: a DPI bucket or the disk hovering at its threshold must not page, and start an agent turn, on every flap.
  - **Problem 2:** a single check's streak breaks when it returns None (two failures hours apart used to make "two in a row"). A check that raises changes nothing. An open key loaded from `alert_state` that no check reports and no prefix covers (a single check whose problem healed while the bot was down) heals like any other, except on a tick where some check raised.
  - **Problem 12:** the protocol family gets ONE agent turn per tick (`_kick_protocol_batch`). The reply is stored on every alert row of the tick and posted once. At most `PROTOCOL_AGENT_MAX_CONCURRENT` (2) such turns run at once. A batch of both families is labelled by its full keys (`inbound_drop:ws+protocol_down:hy2`).
  - A failed or empty agent turn posts «🤖 Агент не ответил по <key>: <why>. Сводка без агента — /protocols» where the alert went (dashboard-only alerts stay log-only).
- **Problem 8:** a probe-demoted protocol without a judged window this run (thin, absent) is not "quiet". Its good streak waits; until now it came back within the hour on no evidence.
- **Problem 10:** job `ai_sessions_cleanup` drops one-shot agent sessions (`proto-alert:`, `dpi-alert:`, `sos:`, `dpi-daily:`) older than 7 days and keeps the admin's `pm:` / `topic:` conversations. It first runs 15 min after start (a daily interval alone never came round with a deploy a day). There were 684 rows on 2026-11-10, 592 of them dpi_hsfail turns. **Problem 11:** HealthChecker's dead `get_recent_health` / `get_health_summary` are removed.
- **Retention:** `outbound_bulk` goes with `outbound_health` (30 d), and `exit_reports` with `dpi_metrics`.
- **Tests:** `tests/integration/test_probe_signals.py` (the shared rules, the same rows judged by all four readers, the pager and the monitor, the prober against a local forward proxy), `test_alert_state.py`, `test_inbound_drop.py`, `test_alert_no_verdict.py` (the review's cases: no verdict, the baseline, restarts, cooldown and ack scope, orphans, the reporter keys), plus `test_gen_probe_config.py` (reserve) and the schema tests. Updated: the agent-failure tests (now one silence line) and `/sos`'s verdict test (the shared quarter). 42 + 22 mutants killed, restored by reverse text replacement with a hash check.
