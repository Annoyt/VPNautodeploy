# §51. New protocols and fingerprints: per-user TLS fingerprint, VLESS XHTTP Reality, SSH emergency path (2026-11-11, plan F, package E)

Package E of `docs/IMPROVEMENT_PLAN.md` section F. **All of it is off until configured.** Unset settings leave every profile byte-identical.

- **E1, TLS fingerprint** (`bot/services/tls_fingerprint.py`). `TLS_FINGERPRINTS` (env, comma-separated, compose passes it) is the pool; each user gets one value by sha256(uuid), stable across fetches.
  - Accepted values are the ones every core we serve knows: chrome, firefox, edge, safari, ios, android, 360, qq, random. Unset or unusable means chrome.
  - Used by every builder that had `chrome` hard-coded: sing-box utls (Reality, ws, the ShadowTLS frontend, RU-exit / RU-zone), the Clash form, the xray form, the DE reserve (`fallback_node.py`) and the share links (`vpn.py`). The probe user's value is whatever its uuid picks.
- **E2/E3, VLESS + XHTTP + Reality, protocol `xhr`.** One multiplexed HTTP/2 session instead of a TLS handshake per connection.
  - Settings: `XHR_SNI` (empty = off everywhere), `XHR_PATH` (/xhr), `XHR_PUBLIC_KEY` / `XHR_SID` (default: the main inbound's), `XHR_PORT` (client-facing, default `ENTRY_NODE_PORT`), `XHR_MAX_CONNECTIONS` (3; mihomo `reuse-settings`, xray `xmux`), `PROBE_PROXY_MIHOMO_HOST` (the probe sidecar).
  - Builders: Clash (`network: xhttp`, `xhttp-opts`), the xray format, `vless://…type=xhttp` links. **No sing-box form**: sing-box has no XHTTP, and `build_singbox_config` drops any outbound with an XHTTP transport (`CLASH_ONLY_TRANSPORTS`). So Hiddify and Karing never see it, which is NekoVPN / FlClash / Hiddify 5 territory. In the Clash profile only for the NekoVPN app (its User-Agent): an older FlClash core may refuse the whole profile over a network type it does not know.
  - Tier paid (`PROTOCOL_TIER`; the owner's call). **Opt-in** (`OPT_IN_PROTOCOLS`): `get_cascade_config` lists it disabled until the operator switches it on in the cascade editor, because an automatic "enabled" on deploy would hand out a server nobody runs.
  - Lockdown order: after stls (`ws, stls, xhr, reality, hy2, hy2t`).
  - **Probe:** sing-box cannot probe it, so a second sidecar runs on mihomo, `probe-proxy-mihomo` (compose profile `xhr`, `metacubex/mihomo:v1.19.33`). Its config comes from `scripts/gen_probe_config_mihomo.py`: one HTTP listener per protocol bound to its proxy (`listeners[].proxy`), :18087 (and :18088 for the SSH path since 2026-11-15, E4). `HealthChecker` probes `xhr` there (`PROBE_PROXY_MIHOMO_HOST`), and like the DE reserve writes nothing while that sidecar has no inbound. The sing-box generator skips xhr. A sidecar that does not answer at all (not created, stopped, its name unresolvable) writes no rows: an unresolvable name used to read as a plain error, i.e. "xhr dark".
  - **The server: not a panel inbound (review of E).** The relational panel keeps one flow per client and gives it to every VLESS inbound of the client; xray rejects a Vision-flow account that sends no flow with TLS inside ("account is rejected since the client flow is empty") — the reason the CDN inbound is VMess. A VLESS + XHTTP inbound in the panel would therefore reject every user, and its attach step rewrote shared client records (the 2026-09-01 flow-wipe class). `scripts/setup_xhr_inbound.py` and the bot's `XHR_INBOUND_ID` attach are removed. The server is `xhr-exit` below; `xhr` stays switched off in the cascade until it is deployed.
  - **The server: `xhr-exit`, an xray of its own on exit** (`scripts/setup_xhr_exit.sh`, root, on EXIT; `bot/services/xhr_exit.py`; 2026-11-11, after package E). **Deployed 2026-11-12** (`XHR_SNI` gateway.icloud.com). xhr stays off in the cascade until the owner switches it on in the editor; its probe runs on `probe-proxy-mihomo` since 2026-11-13, and once xhr is on the healthcheck also watches the container and its sync (§50).
    - xray `ghcr.io/xtls/xray-core:26.6.22`, pinned by digest. Setup refuses an image without a digest or with xray 26.7.11 or later: mihomo does not keep Reality compatible past it. VLESS + XHTTP (`mode auto`, `XHR_PATH`) + Reality on `XHR_EXIT_PORT` (8446), flow-less clients, keys and short id of its own, generated once (`/etc/xhr-exit/keys.env`, root-only). Setup measures the dest from exit: TLS 1.3, h2, certificate record ≤ 8000 B (§23).
    - Only through entry's haproxy: SNI `XHR_SNI` → exit:8446 with `send-proxy-v2`. The inbound requires the PROXY header (`sockopt.acceptProxyProtocol`), so a direct connection gets nowhere, and xray sees the client's address.
    - The container: its own bridge network (its loopback is not the host's, where the panel and 3x-ui's API inbound listen), the image's user 65532, `--read-only`, `--cap-drop ALL`, `no-new-privileges`, 128 MB, rotated json logs, IPv6 off. The egress refuses private, loopback, link-local and CGNAT destinations (a name is resolved and checked too), BitTorrent and SMTP :25. The script never touches the 3x-ui container or its compose file; in the panel's database it writes only the traffic counters (Traffic, below).
    - **Users:** `GET /api/xhr/users` (the exit report's token) every 2 minutes, from a root timer that runs a root-owned copy (`/usr/local/sbin/xhr-exit-sync`, §36). The list: xhr switched on in the cascade and in the user's tier (`get_cascade_order`'s own answer), narrowed to `ru_exit.is_eligible` (paid and not lapsed, or a payer's open ticket), the rule the RU-zone and the SSH exit ask too; the panel then has the last word (Traffic, below). Everyone listed has xhr in their profile; the profile also carries it for a lapsed payer and a demo user's ticket, and there it fails. Uuids only: VLESS checks the uuid itself, so no hash can stand in. xray logs a user under the SSH exit's name `n<12 hex>`. A read error answers 503, never an empty list.
    - **Keys cross-check:** the answer also carries what the profiles hold (sni, pbk, sid, path). When the bot hands out other ones, the sync applies the users and fails with the `.env` line to fix. An unset `XHR_PUBLIC_KEY` falls back to the main inbound's key, and this is where that shows.
    - **The sync:** a deterministic config, a new container only on a change (a second of reconnects for xhr users), `xray run -test` before the live config moves; a container that does not come back, or comes back crash-looping, is rolled back. A list that suddenly reads 0 users is not applied by the timer (a hand-run setup applies it). A bot that does not answer (unreachable, 5xx) leaves the users as they are and still brings a stopped container back; 403, 404 and junk fail the unit. The token reaches curl through stdin, not argv.
    - **Env files are data:** the script reads KEY=VALUE files with `read_env`, never sources them. Its first version sourced `/etc/xhr-exit.env`, and a test value `;reboot` rebooted the developer's laptop twice (a desktop session may reboot without sudo). The test harness puts tripwires for reboot / shutdown / poweroff / halt first in PATH.
    - **Rollout, by the owner:** (1) `/etc/xhr-exit.env` on exit: `BOT_URL`, `DPI_REPORT_TOKEN`, `XHR_SNI` (a dest of its own, not a name entry's haproxy already routes), and `XUI_DB_PATH` only if the panel's database is not in the 3x-ui volume; (2) `setup_xhr_exit.sh` checks that database, then prints the haproxy lines, the `.env` values and a DOCKER-USER rule (a published docker port bypasses ufw); (3) the lines into entry's haproxy, `haproxy -c`, reload; (4) the values into entry's `.env`, recreate vpn-bot (`--no-deps`); (5) the probe sidecar (`gen_probe_config_mihomo.py`, compose profile `xhr`; dark until step 6, which pages nothing: xhr is off for the pager until switched on, §48); (6) xhr on in the cascade editor. `--print` repeats the lines; `--remove` takes the container and the timer away (keys stay).
    - **Traffic** (2026-11-11, after #49): xhr bytes count against the user's quota in the panel, like every panel protocol, and a user the panel has switched off loses xhr too.
      - **Counters.** The rendered config turns on xray's per-user counters (`stats`, `policy.levels.0.statsUserUplink/Downlink`) and an API with `StatsService` only, on `127.0.0.1:10085` in the container's own network namespace. The routing blocks port 10085 for users by its number: a name that passes the address check may point at loopback when it is dialed (DNS rebinding), and a user who reached the API could reset the counters.
      - **Read first.** Every run reads and resets the counters (`docker exec xhr-exit xray api statsquery -s 127.0.0.1:10085 -pattern 'user>>>' -reset`) before anything can recreate the container (a new xray counts from zero), and once more right before a recreation; `--remove` reads them before the container goes. A sync that cannot read the counters of a running container does not recreate it: users unchanged, the run fails. A stopped container, or a config without the API (an older render), has nothing to read.
      - **Pending file.** The bytes go into `/etc/xhr-exit/traffic.pending` at once (root-only, written by a rename), and only then into the panel. The file is checked before the reset: a damaged one stops the read, leaves the counters in xray and is never overwritten. An answer from xray that cannot be parsed goes to the journal whole, because the counters may be reset already.
      - **Into the panel.** Label `n<12 hex of sha256(uuid)>` → the panel client with that uuid (the relational `clients` table first, each inbound's `settings` for what it lacks) → its email → `client_traffics` `up += uplink`, `down += downlink`, `last_online` raised, in one `BEGIN IMMEDIATE` transaction, as `hy2-traffic-collector` does (§26). A locked panel, or a uuid it has no client or no accounting row for, keeps the bytes pending for the next run (a lost client the bot puts back gets them); bytes no client takes in 31 days are dropped with a line. Delivery is at least once: a run killed between the commit and the pending file's rewrite counts that window twice. The last seconds of a container that dies on its own die with it.
      - **The panel's word.** A user the bot lists stays out of the config while the panel has switched it off (`client_traffics` enable = 0, up + down ≥ total > 0, or an expiry in the past; total 0 is no limit, a negative expiry counts from first use) or has no client for its uuid, and comes back once the panel lets it in again (the monthly reset, a payment). This run's xhr bytes go in first, so a quota spent on xhr counts at once; it holds while the bot does not answer too. The read is read-only (`mode=ro`, `query_only`); one that fails, or that finds none of the listed users in the panel, leaves the users as they are and fails the run. A bot that lists nobody still waits for a hand-run setup; a panel that switches everyone off does not.
      - **x-ui.db:** `XUI_DB_PATH` (default `/var/lib/docker/volumes/vpn-bot_3xui-data/_data/x-ui.db`, the 3x-ui volume, as for hy2-traffic-collector). Setup refuses a file that is not a panel database with `client_traffics` and clients, and keeps the path in `server.env`. The path goes into the sqlite URI quoted, and `mode=rw` never creates a file.
      - Still unmetered: the RU-zone and the SSH exit, which is why they stay paid-only. The bot still lists only `is_eligible` payers for xhr; now that xhr is metered, the profile's own tier rule (a demo user's ticket too) would do — the owner's call.

- **E4, SSH as the paid users' emergency path** (`bot/services/ssh_exit.py`; deployed 2026-11-12: `ssh-exit` on exit :22022). Russian networks are reported to freeze TCP to foreign hosting after ~16 KB, and SSH is reported exempt.
  - Only in the **emergency profiles** (`lockdown=True`: lockdown mode, `/sub?emergency=1`, the SOS kit), last, never in Calls (TCP only). Only for `ru_exit.is_eligible` users (paid, not lapsed), since the path has no traffic accounting. In those it is the LAST RESORT: the tail of Clash `Cascade` and both manual picks, never sing-box `auto` or Clash `Auto` (it skips entry and would often win a speed test). Hiddify, which has no groups, balances over it like any other server.
  - Credentials are derived, never stored: user `n<12 hex of sha256(uuid)>`, password HMAC-SHA256(`SSH_USER_SECRET`, uuid) base64url 32 chars. The server's host key is pinned (`SSH_HOST_KEY`). Other settings: `SSH_EXIT_HOST`, `SSH_EXIT_PORT` (22022).
  - `GET /api/ssh/users` (the exit report's token) returns SHA-512 crypt hashes only: no password, no uuid. A read error answers 503, never an empty list.
  - `scripts/setup_ssh_exit.sh` (root, on EXIT): an alpine sshd container that only forwards (`PermitTTY no`, `ForceCommand /bin/false`, `AllowTcpForwarding local`, group `vpn`). A 2-min timer syncs users from that endpoint through a root-owned copy of the script, and refuses to drop every user on an empty list unless forced. It prints `SSH_HOST_KEY`. Review of E: forwarding only to client ports (`PermitOpen` 80, 443, 853, 993, 995, 465, 587, 5222, 5223, 8080, 8443 — no SMTP 25); the container firewalls its own egress at start (NET_ADMIN in its netns, fail closed): no private, link-local, CGNAT or loopback destination (the host, other containers, a cloud metadata service), no :25; public resolvers, IPv6 off. A user the bot drops has its sessions killed (`pkill`), not only its account. The last list applied is kept root-only in `/etc/ssh-exit/users.plan` and applied at container start, so a re-run of setup locks nobody out. The base image is digest-pinned; the sync checks the container is running; a run from the installed copy works. The hashes are SHA-512 crypt computed in Python (`ssh_exit.sha512_crypt`; the stdlib `crypt` module is gone from 3.13), checked against glibc.
