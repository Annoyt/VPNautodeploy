# §54. The bot token from the dashboard: Settings → «Токен бота» (2026-11-11)

The owner asked to change the Telegram bot token from the dashboard. The case it is for: the token leaked, @BotFather revokes it and issues a new one, and the bot has to run on the new one without ssh. Code: `bot/services/bot_token.py`, `bot/config/secret_store.py`, `bot/utils/token_envelope.py`.

- **Subscription links no longer follow the bot token.** A /sub link was `HMAC-SHA256(BOT_TOKEN, uuid)[:32]`, and every other link a user holds comes from it (/open, /app, /kit, the Clash providers, /probe, the app's mirrors). A new token, from the dashboard or by hand in .env, would have changed all of them at once. At its first start the bot now pins the key into `secrets/sub_token_secret.json` next to bot.db: the `BOT_TOKEN` of that start, so every link stays what it was. `Settings.SUB_TOKEN_SECRET` reads it; `SubscriptionService.derive_token` signs with it (`secret_store.sub_token_key`; a config without it, e.g. a test's Mock, still signs with `BOT_TOKEN`).
  - Never re-pinned: an existing file is never rewritten. An unreadable one is reported (critical) and left alone, as is a missing one after any dashboard change (`bot_token*.json` present): the old key cannot be told from the current token, so restore the file from a volume backup.
- **Where the new token lives.** The container cannot edit the host's .env, so `secrets/bot_token.json` (0600, dir 0700, owner the bot's user) holds it, with the sha256 of .env's `BOT_TOKEN` at the change. `Settings` runs on it while .env still holds that value (`BOT_TOKEN_SOURCE = 'dashboard'`, `BOT_TOKEN_ENV` = .env's). Whoever edits .env later has the newer word: .env wins and the bot moves the file aside at startup (`bot_token.superseded-<ts>.json`, kept for recovery). Writing the new token into .env is therefore safe at any time.
- **Same bot only.** The bot id before the colon must match. A different bot is a move (users must /start it, the group needs it as an admin, Stars payments and the app's t.me links stay with the old one), and a dashboard that installs any token would let a leaked admin link run the service on a bot of its own and sign admin links for it.
- **The change** (`POST /api/admin/bot_token/challenge`, then `/apply`, both admin + rate limit; `GET /api/admin/bot_token` is the status and never carries a token):
  1. The page seals the token (below).
  2. The bot checks the format and the bot id.
  3. getMe through the `TG_PROXY_URLS` entries in order, two tries of 10 s each (`check_token`; no outage bookkeeping). "Unreachable" names every entry with its last error, by type only: requests' messages carry the URL and the token. The status (`GET`) asks once per entry: it shares asyncio's default pool with /sub. Until 2026-11-13 it was one 8-s try per entry and only the last entry's error: exit's tinyproxy, which reaches api.telegram.org over IPv6 first, hung once, and the dashboard blamed the dead DE proxy.
  4. The subscription key must be pinned.
  5. The file is written, `admin_actions('<admin>', 'bot_token_set', 'bot:<id>')`, and a restart in place: after 1.5 s SIGTERM to itself (the `docker stop` shutdown), then `main` execs the same command (`sys.orig_argv`) — no dependency on the container's restart policy; if the shutdown hangs 45 s, it execs anyway.

  Any failed check changes nothing. One change per process. The answer carries an admin link signed with the new token; the page switches to it and waits until the new process answers.
- **After the restart** the bot posts once to TOPIC_AI (the PM only if the topic fails): the token changed, links did not, and what is left by hand — `BOT_TOKEN` in `/opt/vpn-bot/.env` on **exit** (the memory watchdog notifies with it) and on entry. The Hermes guard reads the dashboard's file itself (`BOT_TOKEN_OVERRIDE`, the same rule as `secret_store.effective_bot_token`, mirrored because it runs as root and must not import the bot's code; a test runs both on the same files). The skills mint admin links with `Settings().BOT_TOKEN`, not `os.environ`.
- **The order matters:** open the section, THEN revoke in @BotFather. After the revoke the bot cannot send a new /admin link, and a Mini App opened after it carries initData signed with the new token, which the old process cannot check. The status offers a link (`?link=1`) that keeps working through that window.
- **The page seals the token** (`bot/utils/token_envelope.py` ↔ `app.js sealBotToken`): it was built while exit's Caddy reached entry:8080 over plain HTTP (`reverse_proxy 130.49.146.10:8080`), when whatever the dashboard posted crossed the public internet in the clear. ffdhe2048 Diffie-Hellman (RFC 7919; the test derives the prime from its formula), HKDF-SHA256, an HMAC-SHA256 keystream and tag; one-time shares, 10 min, refused when reused. Stdlib only (`cryptography` stays dev-only). It stops someone who records that hop, not someone who can change it — they could swap the share or the page's JavaScript, which crosses the same hop. **The hop itself has been TLS since 2026-11-11** (§53): every dashboard response (users, contact emails), admin link and /sub profile now crosses it encrypted to a pinned certificate, and the sealing stays as a second layer.
- **Deploy:** the bot (`deploy_to_entry.sh`; the first start pins the key); the Hermes guard (`deploy_hermes_host.sh`) and the skills (`deploy_hermes_skills.sh`) for their parts. Never print `secrets/` (hermes/AGENTS.md, the skills).
- **Tests:** `tests/integration/test_bot_token_change.py` (real sqlite and `Settings`; a restart = a new process on the same data dir), `tests/unit/test_token_envelope.py`, `TestBotTokenOverride` in `tests/unit/test_hermes_model_guard.py`, `TestBotTokenSettings` in tests/e2e (Chromium's WebCrypto seals, the bot opens).
