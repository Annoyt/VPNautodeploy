# §49. A demotion that reaches every client (2026-11-11, plan F, package C)

Until now a demotion took effect only in the Clash profile's Cascade/Auto. Karing kept the server in its `auto`, Hiddify kept balancing over everything, a hand demotion was "restored" by the monitor within the hour, and flapping targets came back every hour. Package C of `docs/IMPROVEMENT_PLAN.md` section F.

- **C1, sing-box `auto`.** `build_singbox_config(demoted=…)` leaves the demoted servers out of the `auto` urltest; the `proxy` selector keeps them for the manual pick. As in Clash (`_clash_excluded`), a demotion of every cascade protocol excludes nothing. Only Karing reads these groups.
- **C2, Hiddify** (`build_singbox_config(hiddify=True)`; `/sub` sets it when the User-Agent contains "hiddify"). hiddify-core 4.1.0 (`v2/config/builder.go`) drops every selector/urltest of a profile. It builds `select` + two balancers from ALL outbounds except those whose tag contains **`§hide§`**.
  - The bot's own profile was run through the real core (`hiddify-cli build`). Hidden outbounds stay in the config (detours keep working) but never enter `select` / `balance` / `lowest`.
  - Without the marker, the core also balanced user traffic onto **ShadowTLS's frontend outbound** (a detour, not a proxy).
  - Marked for Hiddify: the demoted servers, the ShadowTLS frontend (always) and the RU-exit outbound of `lang='en'` profiles. Detours, groups and route rules follow the rename. Other clients keep plain tags.
  - **In Hiddify a demotion is removal:** a hidden server is gone from its manual pick too. So the demoted servers are hidden only while at least two cascade servers stay visible (`HIDDIFY_MIN_VISIBLE`, the DE reserve not counted); otherwise Hiddify sees every server, as before. Hiddify gets no personal demotions (C3): its user's telemetry came from another device. The SOS kit's `.json`, the file Hiddify imports, is built the same way.
  - Test `TestHiddifyCore` in `tests/integration/test_demotion_acts.py` runs the core when `HIDDIFY_CLI` (or `/tmp/nekovpn-test-cache/hiddify-cli-4.1.0`) exists, and skips otherwise. To build it: `git clone --branch v4.1.0 https://github.com/hiddify/hiddify-core`, `git submodule update --init --recursive`, then in `golang:1.25-alpine` (exactly Go 1.25: psiphon-tls panics on a newer runtime) run `CGO_ENABLED=0 go build -tags with_gvisor,with_quic,with_wireguard,with_utls,with_clash_api,with_grpc -o hiddify-cli ./cmd/main`.
- **C3, personal demotion** (`bot/services/personal_demotion.py`).
  - Rule: the user's client checked in through other cascade protocols in ≥ 12 distinct 10-min slots of the last 3 h (≈ 2 h of an open app; slots, not rows — a paid profile checks three other protocols at once, and twelve rows were forty minutes), and not once through this one, which it did pass within 7 days. Then that protocol leaves the user's Cascade/Auto/`auto` (and sinks in Calls); it stays in the manual pick and in telemetry, and the first row through it again lifts the demotion at the next profile fetch.
  - Silence is no signal (a closed app leaves no rows anywhere). The DE reserve counts for nothing.
  - It is per user, not per device: the rows carry our egress, not the device's network.
  - Applied on `/sub` (both formats; read on a worker thread, not on the event loop) and in the SOS kit's Clash profile; not for Hiddify (above).
- **C4, clients across networks:** rule `client_dark_global` (ranked after the probe rules). ≥ 2 dead clients in ≥ 2 different known networks, nobody passing → a global demotion. R6's guards apply: a live row through another cascade protocol, the protocol offered to the client. On 2026-11-10 two clients sent telemetry, one on MegaFon and one on ER-Telecom, so R6 (three per network) could never fire.
  - For both client rules (R6 and R6g), a client is dead on a protocol only if it passed that protocol within 7 days (`CLIENT_DARK_SEEN_DAYS`). A protocol the operator just switched on is in nobody's profile until the next refresh (6–24 h), and it read as dead for every telemetry client: a global demotion within 20 min.
  - A client-rule demotion comes back only when some client passes the protocol again. With no client evidence at all (every app closed) the rule has no verdict, and the demotion waits.
- **C5, growing pause.** Target entries keep `demotions` (timestamps within 24 h). A target demoted again within a day needs `RESTORE_AFTER_GOOD × 2^(n−1)` good evaluations to come back, capped at 48 (8 h): 6 → 12 → 24 → 48. On 2026-11-10 prod had AS31133:reality demoted 12 times, each back after ~1 h. Restores have their own cap (`MAX_RESTORES_PER_RUN` = 2) and no longer wait behind demotions (problem 15).
- **C6, hand demotions** (`bot/services/cascade_manual.py`, `app_settings.cascade_manual`, apart from the monitor's `cascade_auto`).
  - `/cascade demote <proto> [ASN] [ttl]`: ttl `30m` / `6h` / `2d`, default 6 h, at most 7 d. `/cascade restore <proto> [ASN]` drops the hand entry only; a monitor demotion of the same target stays and the reply says so. `/cascade reset` now clears hand demotions too.
  - The ASN takes its `AS` prefix here (a bare `30` was AS30 when the admin meant 30 minutes); a second ASN or ttl and any extra token are refused, nothing written. `/cascade AS31133` lists that network's hand demotions.
  - Writers read strictly: a locked read would have been "nothing stored" and the write would have dropped every other entry. A write that did not land answers «❌» and leaves no audit row. An `until` with a UTC offset is converted, not compared against naive times (that raised and dropped every entry).
  - `MyKeyAnswerHandler.get_auto_demotions` unions the live entries (expired ones are ignored), so /sub, the key card, the kit and `get_cascade_order` honour them. The monitor never touches them.
  - Audit: `cascade_manual_demote|restore`, target `global:<proto>` / `asn:<ASN>:<proto>`.
- **C7, slow probes, normal users.** A probe DEGRADED (R2) is vetoed while that protocol's users keep connecting as usual: in the probe's own window (its newest three runs, 45 min) between half and twice the median of the same 45 min on the previous 7 days, median ≥ 20 (≈ 50 a 2-h block); `dpi_metrics`: reality / cf-ws / ss2022. The veto is logged and lands in `signals['probe']['vetoed']`.
  - Twice the usual is not "as usual": a reconnect storm is many accepted connections. hy2 is never vetoed, because its count is the bot's rollup of auth allows and a storm of them is the failure R4 is built on.
  - A baseline day the exit did not report is skipped, never a zero (≥ 4 usable days or no veto). A window with no rows gives no veto, and the probe rule stands. A dark probe is never vetoed.
